**Findings**

Relevant guidance was found in two Slack threads:

- **`#fins-ai-challenge-team-cool` — August 27, 2026**
  - Kateryna Savchyn provided a Unity Catalog SQL custom guardrail function:
    - `reyden_whisperers_catalog.meridian_ai_gateway.guard_block_all_data(...)`
    - Returns `STRUCT<result STRING, reason STRING>`.
    - Uses case-insensitive matching for phrases such as `"all customers"`, `"every account"`, `"entire dataset"`, `"read everything"`, `"unfiltered"`, `"no filter"`, `"select *"`, and `"list all customers"`.
    - Deny response: `"Blocked: request attempts to read all/unfiltered Lakebase data"`.
  - A refined version uses `RLIKE` against the event payload and includes patterns for:
    - all data/customers/accounts/records/rows/balances
    - entire dataset/table/database
    - whole table/dataset
    - `read everything`
    - `unfiltered`, `no filter`
    - `select *`
    - `dump all` / `dump the`
    - `list all customers`
  - The same thread explicitly instructs running one blocking and one passing `SELECT` test and confirming the exact return shape expected by the AI Gateway custom-guardrail policy.
  - Representative snippets:
    - `"Use as an AI Gateway custom guardrail... patterns like 'all customers' ... 'select *' ... Use a case-insensitive RLIKE."`
    - `RETURNS STRUCT<result STRING, reason STRING>`
    - `THEN NAMED_STRUCT('result', 'deny', 'reason', 'Blocked: request attempts to read all/unfiltered Lakebase data')`
  - Thread: [Slack thread](https://databricks.enterprise.slack.com/archives/C0BT6DQMJAE/p1787868159121629?thread_ts=1787849345.301679&cid=C0BT6DQMJAE)

- **`#streamline-telco-hackathon` — August 27, 2026**
  - Omri Sokol described a gateway-enforced alternative/defense-in-depth approach:
    - Route the coding agent through a Unity AI Gateway endpoint.
    - Apply a **128K TPM per-user rate limit**, which produces a `429` and stops a runaway “read all Lakebase data” request.
    - Use a `$0.05` budget block as a second line of defense.
    - Capture the result in the inference table, including the `429` on the all-data read.
  - Representative snippet:
    - `"The 'read all Lakebase data' runaway is stopped by the 128K-TPM per-user rate limit (429); $0.05 budget block is the second line."`
  - The follow-up feedback in the same channel says the implementation still needed a committed test proving that the guardrail blocks a runaway all-data read, and evidence that the governed Slack MCP was configured and routed through the gateway.
  - Threads:
    - [Gateway/rate-limit message](https://databricks.enterprise.slack.com/archives/C0BSYR6M7LK/p1787843667640039)
    - [Feedback message](https://databricks.enterprise.slack.com/archives/C0BSYR6M7LK/p1787851541230389)

**Bottom line**

The clearest proposed solution is:

1. Put the agent behind an AI Gateway custom guardrail.
2. Inspect the request/event payload with a case-insensitive `RLIKE`.
3. Deny all-data patterns, including `SELECT *`, unfiltered reads, “dump the entire table,” and equivalent natural-language requests.
4. Return the gateway-compatible `STRUCT<result, reason>` decision.
5. Add a per-user TPM rate limit and budget cap as defense in depth.
6. Validate with both a blocked test and an allowed filtered-read test, and record gateway-side enforcement in the inference table.

Slack also indicates that, as of the August 27 feedback, the committed proof of the blocked all-data test and governed Slack MCP routing was still missing; the guidance existed, but the end-to-end evidence was not yet complete.
